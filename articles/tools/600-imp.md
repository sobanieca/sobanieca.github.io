`jsonr`, `sqlr`, `tunnelr`, `todoer` and `yate` all share one idea: a single
binary that does its job and doesn't get in the way. This one is the project
I've been dreaming about for a long time - the same idea, applied to frontend
development.

I was always disappointed by the state of frontend development tools. The
ecosystem is very fragmented: a package manager, a bundler, a dev server, a
test runner, a linter, a formatter, a framework and a router, each with its own
configuration, plugins and upgrade path. Before you write a line of your app,
you spend time making all of them work together. And then you wait for the
build step.

I always wanted one binary that lets me focus on building the app, even at the
cost of not having many fancy features. Making a frontend app should be as
simple as downloading a single file and focusing on the value of your app,
without struggling with tool configuration and waiting for a build. So I built
[imp](https://imp-ui.com).

> This blog is built with `imp` too.

**Why `imp`?**

- **All-in-one toolkit:** One binary is the dev server, the component library,
  the state, the router, the test runner, the linter, the formatter and the
  bundler.
- **No build step while you work:** `imp start` serves your files exactly as you
  wrote them. You edit a file, the browser reloads, and the source you typed is
  what runs.
- **Built on web components:** An `imp` component is a real custom element that
  renders into its own shadow root, so its DOM and CSS are isolated.
- **Dependencies live in your repository:** `imp install` vendors a package
  once. A fresh clone is the whole app, and it runs without the network.
- **Ready for AI agents:** `imp skill` prints manuals written for an AI agent,
  so you can build an app from start to end without writing code by hand.

### Why web components

I have been experimenting with web components for about 10 years, and I always
wanted a tool based on them. They are part of the browser, so there is no
framework runtime to learn, upgrade or replace. The name of a component is its
HTML tag, so what you see in the element inspector is exactly what you wrote.
`imp` adds what the platform doesn't give you on its own: state, routing,
theming and a lifecycle you can rely on.

### Why SPA

I'm a huge fan of single-page applications. I think they solve the stateless
nature of HTTP very nicely - the state of the app lives in the browser, and the
backend only answers API requests. They are also very tempting to deploy: the
whole frontend is a set of static files that you serve from a CDN. The user sees
the app immediately, even when the backend is a bit slow.

That's why `imp` only needs a build when you ship. `imp build` packs the app into
a minified bundle for any static host or CDN, with lazily loaded modules in
chunks of their own.

### Install

Linux and macOS:

```bash
curl -fsSL https://imp-ui.com/install.sh | bash
```

On Windows, in PowerShell:

```powershell
irm https://imp-ui.com/install.ps1 | iex
```

### Your first app

```bash
imp init my-app
cd my-app
imp start
```

`imp init` scaffolds a small working app: a frame, a router and a click counter,
with a unit test and an end-to-end test. It never asks a question, so it's safe
to give to an AI agent as a first step. `imp lint`, `imp fmt`, `imp test --unit`
and `imp test --e2e` all pass before you change a line.

To let an agent build the rest, create the `imp` skill for Claude Code, Codex
and Cursor:

```bash
imp skill --init
```

When you're ready to ship:

```bash
imp build
```

and upload `dist/` to any static host.

### Good to know

- `imp` is experimental. Until version `1.0.0`, any part of it can change.
- `imp.json` is the only config file, and it's optional.
- [imp-examples](https://github.com/sobanieca/imp-examples) holds complete apps
  built with `imp`, such as
  [Beacon](https://examples.imp-ui.com/observability/), an observability SPA,
  and [Brickfall](https://examples.imp-ui.com/brickfall/), a game that installs
  as a PWA.

### Conclusion

`imp` doesn't try to have every feature of the big frameworks. It's meant for
building an app without assembling a toolchain first: one binary, web
components, no build step while you work, and static files when you ship.
