# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with
code in this repository.

## Fine tuning articles

When asked to fine tune given article perform grammar/syntax corrections. Do all
that is possible to keep original intent/context. Double check all guidelines
mentioned in article if they are correct. If not report it immediately. Ensure
that fine tuned article has similar tone to other articles.

Articles are grouped into categories, with the numeric prefix (100, 200, 300...)
defining reading order. Treat the category as a single continuous walkthrough,
not a bag of independent posts. When reviewing or editing an article, check
that:

- The opening of each article builds on the outcome of the previous article in
  the same category. The reader should feel they are picking up where the last
  article left off - not starting from scratch. Read the neighbouring articles
  (the one before and the one after) before editing so transitions line up.
- Within an article, each section and step is framed as a natural consequence of
  what came before it. The reader should never have to ask "why are we doing
  this now?" - the motivation for each step should come from the state or
  problem the previous step established.
- Flag structural gaps: orphaned sections, steps that don't flow from prior
  context, weak openers that restate the title instead of connecting to the
  previous article, or trailing content that doesn't set up the next one.

## New articles

When asked to write or add a new article, always ask the user for a hero image
(unless one was already provided). Every article is expected to have one, named
after the article file (e.g. `300-tunnelr.md` -> `300-tunnelr.jpg`) and placed
next to it. Match existing hero images in cyberpunk/neon illustration style.

## Image sizes

Heroes display at most 512px wide (`.article-hero`) and article content is 800px
wide, so keep images small:

- Hero images: JPEG, max 1024px wide (e.g. 1024x559 or 1024x1024), ~100-170KB.
- Inline images: JPEG, max 1600px wide / 1400px tall, ideally under 150KB.
- Make sure the file extension matches the real format (no PNGs named `.jpg`).

Resize/recompress any provided image that exceeds these limits, e.g. with
ffmpeg:

```bash
ffmpeg -i input.jpg -vf "scale='min(1024,iw)':-2,format=yuvj420p" \
  -map_metadata -1 -q:v 4 output.jpg
```

For inline images, use
`scale='min(1600,iw)':'min(1400,ih)':force_original_aspect_ratio=decrease`
instead.

## Build Commands

The build tooling is the Rust crate `xtask/`, run through the cargo aliases in
`.cargo/config.toml`:

```bash
# Generate src/content/ from articles/ and about.md, then serve with live reload
cargo dev

# Only regenerate the content (after editing an article while `imp start` runs)
cargo content

# Build the static site into dist/ (analytics off)
cargo site

# Serve dist/ locally, with GitHub Pages' extensionless .html lookup
cargo serve

# Everything CI checks: cargo fmt, clippy and tests, imp fmt and imp lint, no
# TODO: left in an article, no oversized image or video
cargo verify
```

After changing anything under `src/`, run `imp fmt` and `imp lint` and fix every
finding. After changing `xtask/`, run `cargo fmt` and `cargo clippy` and fix
every finding.

## Architecture

The site is an **imp** single-page app (https://github.com/sobanieca/imp-ui,
read `imp skill` before writing imp code) whose content is generated by a Rust
build tool (`xtask/`). Each article is a page of its own in the imp application map and a
lazily loaded imp **area**, so a visit downloads only the article it shows.

### Build Pipeline (xtask/)

1. Reads Markdown articles from `articles/{category}/NNN-*.md` with YAML
   frontmatter (`frontmatter.rs` reads the small YAML subset they use)
2. Converts Markdown to HTML with `pulldown-cmark` (`markdown.rs`). Each code
   block becomes a `<div data-code="N">` placeholder, which the article page
   replaces with imp's `codeBlock` (`imp/std/display`), so code is highlighted
   in the browser with the colours of the theme. A fence without a language, or
   one imp does not know (`http`), shows as `text`.
3. Writes generated JS modules to `src/content/` (gitignored, `content.rs`):
   - `site-data.js` - categories, article metadata (no bodies), about page
   - `articles-map.js`, `categories-map.js` - parts of the imp app map, one node
     per page
   - `routes.js` - the screens; each article is
     `area(() => import('./articles/<slug>.js'))`
   - `articles/<slug>.js` - one area module per article, holding its rendered
     HTML and its code blocks
4. Copies hero images to `public/assets/images/articles/` and inline images to
   `public/articles/images/` (both gitignored)
5. Runs `imp build` into `dist/` (`--env prod` for `cargo site --publish`)
6. Writes a copy of `dist/index.html` per route (`articles/<slug>.html`,
   `category/<slug>.html`, `about-me.html`, `projects.html`) with its own title
   and description, plus `404.html`, so GitHub Pages answers every page with its
   HTML (`pages.rs`)

`cargo site` also re-encodes oversized images and videos with ffmpeg
(`assets.rs`); `cargo site --publish` and `cargo verify` only check them.

Article slugs must be lowercase words joined by single dashes: a slug becomes a
camelCase key of the app map, and imp serves it as the kebab-case path again.

### App (src/)

- `main.js` - entry: registers the imp-aly analytics sink (only when the
  `ANALYTICS` build flag is on), applies the themes, adopts the site stylesheet,
  mounts the layout
- `app-map.js` - the imp application map (pages: `/`, `/about-me`, `/projects`,
  `/category/<slug>`, `/articles/<slug>`)
- `layout.js` - sidebar, router, comments section and footer, rendered in the
  light DOM
- `pages/*.js` - one imp component per screen, each with a `*.skill.md`
- `comments.js` - Giscus comments; they live in the light DOM because Giscus
  needs `document.querySelector`
- `links.js` - routes clicks on plain `<a>` links through the router and
  resolves `#fragments` inside shadow roots
- `styles/site.js` - the whole stylesheet as a string: each screen component
  uses it as its `styles` (components render in shadow roots) and `main.js`
  adopts it for the light DOM layout

URLs have no `.html`. Old `.html` addresses are redirected by
`pages/not-found-page.js`.

### Theme System

Light and dark imp themes (`src/themes.js`) are listed in `init` with
`persist: true`. The layout sets `data-theme` on `<html>` from the theme in
force, and the colours are CSS variables in `public/assets/css/site.css` that
inherit into every shadow root.

### Analytics

`imp/analytics` records page views per route. The `alySink` posts them to the
imp-aly server at `https://aly.admware.com` under the app name `sobanieca-blog`.
The `ANALYTICS` flag is declared in `imp.json` and turned on only by
`env/prod.json`, so `imp start` and `cargo site` send nothing.

### Content Structure

Directory structure:

```
articles/{category-slug}/
  NNN-article-slug.md          # NNN = order index (100, 200, 300...)
  NNN-article-slug.jpg         # optional hero image (matches article filename)
  images/                       # inline images referenced in markdown
```

Categories: `general`, `build-anywhere`, `build-on-the-go`, `build-in-terminal`,
`tools`

YAML frontmatter:

```yaml
---
title: Article Title
excerpt: Short description
date: YYYY-MM-DD
---
```

The numeric prefix (100, 200, 300...) controls article order within a category.
Use gaps (100s) to allow inserting articles between existing ones. The `date`
field in frontmatter tracks when the article was last updated and is used for
"most recent" sorting on the home page.

Inline images: reference as `images/filename.jpg` in markdown. Link another
article as `./200-other-article.md` or `../category/200-other-article.md`.

### Deployment

Automatic via GitHub Actions on push to `main` branch: installs imp, runs
`cargo verify` and `cargo site --publish` and deploys `dist/` to GitHub Pages.
